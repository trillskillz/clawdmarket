# Private organization providers: audit and acceptance

Starting local contract 1.95, publishing counter 3/10. This audit does not count
as capability 4. Production 1.90 remains unchanged and all work stays local.

## Current boundaries and gaps

Public discovery/planning/service readiness/reservation/funding require an active
public provider agent. Private providers have no organization access continuation.
Current linked owners exist independently of legacy owner values. Organization
membership and read keys grant no checkout/agent ownership authority. New exact
service approvals do not widen seller availability or wallet authority.

Provider work retrieval/delivery remains funded-party-only and uses immutable
checkout execution terms. Closing/revoking catalog access must stop fresh sends
without hiding original funded work, receipt or refund obligations from parties.

The proof directory/detail and activity trade/rating queries currently read
completed private-agent transactions without a shared publication rule. Names,
service descriptions and transaction references can leak despite hidden registry
entries. Original organization-private orders must remain private even if a
provider later publishes its agent or a share is revoked. Do not enable private
checkout until public projection acceptance covers these paths.

## Proposed usable outcome

A current linked owner of an active private provider agent explicitly offers one
contracted service to a specified organization. Its current organization owner
accepts the exact share, scope and expiry. Both owner identities remain pinned;
transfers or revocation/expiry stop fresh use. A private service is never inferred
from organization/team membership or from a public seller override.

The organization owner, explicit current purchasing participant with matching
department scope, and an assigned currently owner-linked buyer agent can inspect
an authorized private catalog. Ordinary viewers and cmo_ read keys retain their
existing metadata-only surfaces. Provider-owner private management remains
separate. The actual buyer payments credential reserves using the exact accepted
share; approval and every budget/provider/rail/verification restriction still
apply. Start with direct services; public router/workflow discovery cannot gain
private providers through this share until its exact continuation passes.

Freeze the original share in the economic order. Current share, owner, buyer
assignment/department and provider status are checked inside reservation and fresh
funding transactions. Original paid provider dispatch/delivery, buyer acceptance,
settlement and already-sent payment/refund recovery keep existing party access.
No service input, organization identity, private provider name, approval, trade
reference or private completion enters public proof/activity/listing/reputation/
capability discovery after share revocation or a later public agent transition.
Public counters count published records consistently; financial operator health
still includes all original obligations.

## Required acceptance

- Actual API share offer/owner acceptance/private catalog/exact registered buyer
  checkout, dummy-chain-backed payment, separate private provider restart,
  verified delivery, explicit buyer acceptance, exactly-once backed payout and
  released capacity; original share/approval attribution retained.
- Owner/outsider/viewer/read-key/other-agent/scope/reference isolation, current
  both-owner/role/assignment/expiry checks, and every existing budget/rail/provider
  restriction; no copied share, concurrent replay or failed transaction can
  duplicate spending/capacity or silently publish a service.
- Independent share/order races, lost responses and process death recover original
  identities. Revocation/flags stop fresh permission while original paid work and
  sent-proof/refund recovery remain usable.
- Public directory/search/detail/metadata/listing/activity/proof/capability/
  reputation projections omit private records at desktop/mobile sizes, before and
  after original provider becomes public. Private outputs stay party-only.
- Additive migration replay preserves financial history; private CSRF/bounded
  APIs, checked contract/SDK, full predeploy/build/browser gates pass before 4/10.

No live funds, external provider consent, production flags, push or deployment
is authorized. Spending service-account authority remains the following P2.2 work.


## Executed local acceptance (1.96)

All acceptance groups above pass. The original audit began at 3/10; this complete
capability increments the local publishing count to **4/10**. The private service
flow is direct and separately approved by both current owners. It does not
extend public route/workflow/instant authority or read-key/viewer permissions.

Seventeen actual HTTP/domain purchasing/private-provider cases cover registered
buyer/provider credentials, real unforked dummy EVM deposit, private provider
restart/delivery, explicit acceptance, exactly-once backed credit payout and
released capacity. A real sent EVM hash after revoked sharing/closed flags enters
its original confirmed full refund. Separate process races and six private
SIGKILL boundaries retain original share/consent/order identity and rollback.
Fresh owner, role, assignment, department, expiry, provider and consent changes
fail without money or capacity. Private cookie CSRF/body bounds pass.

Public privacy is permanent after provider publication and revoked sharing:
proof metadata/details, activity, underlying listings/checkout, agent work,
capability/reputation evidence and volume omit original private work. The
historical migration preserves old service/order input, MPP method, price and
references. Current buyer and provider retain party-only original receipt/work.
Financial operator history remains complete.

Evidence and final counters are recorded in ROUTING_LAYER_MASTER_PLAN.md:
694 full predeploy cases (689 passed/five expected skips), 33 focused final
acceptance cases, the strengthened historical migration, final build/type/lint
and all 20 built-app browser journeys. No push/deployment, live spending,
production flags, actual MPP transfer, independent provider or semantic claim.
