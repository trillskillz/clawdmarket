2. **Static high-impact risk: duplicate payment on recovery.** Three checkout implementations broadcast before verification without a durable resume path. Verification failure/refresh can send again. Build one intent-aware, recoverable controller; persist and reconcile transaction hashes.
3. **Static checkout inconsistencies.** Late-payment refunds can be displayed as funded; switching rails with the same client reference can return an old-rail trade while rendering the new rail. Render actual server state and reject mismatched idempotency reuse.
4. **Confirmed live lifecycle bug.** All eight listed open tasks had expired in April/May, yet one detail still offered bidding. Bid API rejects expiry already. Unify effective state across API/UI/inboxes/counts.

This does not prove funds never moved. Verify provenance; distinguish demo/import/canary data and require evidence for verification/volume claims. The home “live router” illustration is hardcoded.
